# 主从 Reactor 多线程模型笔记

## 1. Reactor 模式概述
**Reactor 模式**是一种事件驱动的网络编程架构，核心思想是：由一个或多个线程**阻塞等待**多个 IO 事件，事件就绪后**分派**给对应的处理器回调。

- **本质**：将 IO 多路复用 (`select/poll/epoll`) 与事件回调结合。
- **目的**：解决传统“一个连接一个线程”模型在高并发下线程资源爆炸、上下文切换过重的问题。

---

## 2. Reactor 模式的演进

### 2.1 单 Reactor 单线程
- **结构**：一个线程同时负责 **accept**、**读写**、**业务处理**。
- **流程**：
  1. Reactor 线程在 `select/epoll_wait` 上阻塞，监听 `accept` 事件和已连接 socket 的读写事件。
  2. 新连接到来，`accept` 后注册到当前 Reactor。
  3. 连接可读时，同一个线程完成 `read → decode → compute → encode → send`。
- **致命缺点**：
  - 无法利用多核 CPU。
  - 一个耗时业务会阻塞所有其他 IO 事件。

### 2.2 单 Reactor 多线程
- **结构**：一个 Reactor 线程负责 accept 和 IO 读写，**业务计算**交给 Worker 线程池。
- **改进**：Handler 读取数据后，将业务处理封装为任务丢给线程池，自己立刻返回继续处理 IO 事件。
- **依然存在问题**：
  - 单个 Reactor 线程既要 accept 又要承担大量连接的 IO 读写，在大规模连接（数万以上）时成为瓶颈。
  - accept 可能被大量读写事件影响。

### 2.3 主从 Reactor 多线程
- **结构**：
  - **MainReactor**：只处理 `accept` 事件。
  - **SubReactor 组**：每个 SubReactor 负责一部分已连接 socket 的所有 IO 事件。
  - **Worker 线程池**：处理非 IO 的耗时业务。
- **优势**：
  - **分离 accept 和 IO**：MainReactor 可极速接受新连接，不阻塞老连接。
  - **IO 负载分片**：多个 SubReactor（通常等于 CPU 核数）各自管理一部分连接，单 epoll 监听数减少。
  - **充分利用多核**。
  - **无锁串行化**：每个连接在整个生命周期中绑定唯一的 SubReactor，其 IO 事件串行处理。

## 3. 主从 Reactor 核心角色与架构

### 3.1 餐厅比喻理解

| 现实角色 | 主从 Reactor 对应 | 职责 |
|----------|-------------------|------|
| 迎宾员   | MainReactor       | 只在门口迎接新客人（accept），迅速分配给服务员 |
| 服务员   | SubReactor        | 每人负责几张桌子（一组 socket），处理客人点菜/倒水/上菜（读/写） |
| 厨房     | Worker 线程池     | 做耗时菜品（业务计算），不直接接触客人 |
| 任务本+铃铛 | 任务队列 + eventfd | 厨房做好菜后，写纸条+按铃通知服务员上菜 |
| 每桌固定服务员 | 线程绑定 / 无锁 | 一个客人从头到尾由同一个服务员服务，不会争抢 |

### 3.2 正式角色定义
- **Handle (句柄)**：操作系统资源，如 socket 文件描述符。
- **Synchronous Event Demultiplexer (同步事件分离器)**：`epoll_wait`，阻塞等待多个句柄上的事件。
- **Event Handler (事件处理器)**：回调接口，如 `handleRead()`, `handleWrite()`。
- **Concrete Event Handler**：具体实现，如 `TcpConnection`。
- **Reactor / Initiation Dispatcher**：`EventLoop`，核心循环，负责等待事件并分发给对应的 Handler。

### 3.3 架构图
```
                        Clients
                          |
          +---------------v---------------+
          |        MainReactor            |   (1个或少量线程)
          |    epoll(OP_ACCEPT)           |
          +---------------+---------------+
                          |
               accept & dispatch  (轮询分发)
          +--------+--------+--------+
          |                 |        |
          v                 v        v
   +------------+   +------------+   +------------+
   | SubReactor |   | SubReactor |   | SubReactor |  (多个线程，独立 epoll)

         |                |                |
         +--------+-------+--------+-------+
                  |                |

        +--------------------+
        |  Worker ThreadPool |  (业务计算)
        +--------------------+
```

## 4. 工作流程详解

### 4.1 启动阶段
- MainReactor 创建监听 socket，注册到自己的 epoll 实例，只监听 `EPOLLIN`。
- 创建 N 个 SubReactor，每个 SubReactor 启动独立线程运行事件循环。
- 每个 SubReactor 内部创建自己的 epoll 实例，并注册一个 `eventfd` 用于跨线程唤醒。

### 4.2 接受新连接
1. MainReactor 的事件循环在 `epoll_wait` 上阻塞。
2. 新连接到来，`epoll_wait` 返回，执行 `accept` 获得客户端 fd。
3. 根据轮询（Round‑Robin）选择一个 SubReactor。
4. **不能直接在该线程将 fd 注册到 SubReactor 的 epoll**（跨线程操作 epoll 不安全）。
5. 封装一个“注册任务”放入该 SubReactor 的任务队列，然后写入 `eventfd` 将其唤醒。
6. SubReactor 被唤醒后，在 `processTaskQueue()` 中执行注册：将 fd 以 `EPOLLIN | EPOLLET` 模式加入自己的 epoll，并创建 `TcpConnection` 对象绑定。

### 4.3 读事件处理
1. 客户端发送数据，SubReactor 的 epoll 检测到对应 fd 的 `EPOLLIN` 就绪。
2. 回调 `TcpConnection::handleEvent()`，进入 `handleRead()`。
3. 由于使用边缘触发，**必须循环读取直到 `read()` 返回 `EAGAIN`**，防止漏数据。
4. 读取到数据后，通常需要解码并处理业务。为避免阻塞 IO 线程，将业务封装为 `Task` 提交给 Worker 线程池。
5. IO 线程立即返回，继续监听事件。

### 4.4 业务线程处理与写回
1. Worker 线程收到任务后执行耗时操作（计算、查库等）。
2. 处理完毕后需要发送响应。**Worker 线程绝对不能直接调用 `write()`**，因为：
   - 跨线程写 socket 可能导致数据乱序。
   - 与 IO 线程产生竞争。
3. 正确做法：调用 `TcpConnection::send(data)`。该方法内部判断：
   - 如果当前线程就是连接所属的 EventLoop 线程，直接发送。
   - 否则，将写操作封装为任务，通过 `addTask` 丢回该连接绑定的 SubReactor 的任务队列，并唤醒。
4. SubReactor 线程在任务处理中执行真正的写操作。

### 4.5 写事件细节
1. 尝试直接 `write()`。若一次性写完，直接返回。
2. 若返回 `EAGAIN`（发送缓冲区满），将剩余数据存入连接的**写缓冲区**。
3. 修改 epoll 监听事件，**增加 `EPOLLOUT`**，等待可写通知。
4. 当 socket 再次可写时，`handleWrite()` 被触发，从写缓冲区继续发送。
5. **写完全部数据后，必须立即撤销 `EPOLLOUT`**（只保留 `EPOLLIN`），否则只要缓冲区未满就会一直触发可写事件，导致 CPU 100%。

## 5. C++ 实现关键机制

### 5.1 epoll 边缘触发 (EPOLLET)
- **水平触发 (LT)**：只要缓冲区有数据就持续通知，简单但可能多次唤醒。
- **边缘触发 (ET)**：只在状态变化时通知一次（例如从无数据变有数据）。效率更高，但要求应用程序必须一次把数据读完。
- 实现要点：在读事件中 `while(true)` 循环 `read()` 直到返回 `-1` 且 `errno == EAGAIN`。

### 5.2 eventfd 唤醒机制
- `eventfd` 是 Linux 提供的一个轻量级事件通知文件描述符。
- 创建：`int fd = eventfd(0, EFD_NONBLOCK);`
- 唤醒（任意线程）：`write(fd, &val, sizeof(val));`
- 消费（EventLoop 线程）：`read(fd, &val, sizeof(val));`
- 作用：使阻塞在 `epoll_wait` 的 IO 线程能立即被其他线程唤醒，从而处理任务队列中的注册、写回等操作。

### 5.3 任务队列 (跨线程安全)
- 每个 SubReactor 维护一个 `std::queue<std::function<void()>>` 和一个互斥锁。
- `addTask()`：加锁入队，然后 `wakeup()`。
- `processTaskQueue()`：在 EventLoop 线程中，交换出整个队列，无锁执行所有任务，避免长时间持锁。

### 5.4 写缓冲区与 EPOLLOUT 管理
- 每个 `TcpConnection` 对象持有一个 `std::string writeBuffer_`。
- 当无法一次写完数据时，剩余数据加入缓冲，并开启 `EPOLLOUT`。
- 可写事件触发时继续发送，发送完毕关闭 `EPOLLOUT`。

### 5.5 线程绑定与无锁串行化
- 一个 socket 从创建到销毁只属于一个 SubReactor。
- 该 socket 的所有 IO 回调（读、写、关闭）都只在该 SubReactor 的线程内执行。
- Worker 线程只能通过 `addTask` 间接操作 socket，从而天然避免了多线程竞争，实现了“无锁”设计。

## 6. 完整代码结构解读
（基于前述完整示例代码）

### 6.1 EventLoop 类
- 代表一个 SubReactor。
- 核心成员：
  - `epfd_`：epoll 实例。
  - `wakeupFd_`：eventfd，用于唤醒。
  - `pendingTasks_`：待执行的任务队列。
- 核心方法：
  - `loop()`：事件循环，`epoll_wait` → 处理 wakeup 或 IO 事件。
  - `addTask(task)`：跨线程提交任务，内部加锁并 wakeup。
  - `updateEpollEvent(fd, events)`：修改 socket 监听事件（用于切换 EPOLLOUT）。

### 6.2 TcpConnection 类
- 代表一个客户端连接。
- 核心成员：
  - `fd_`：socket 文件描述符。
  - `loop_`：所属的 EventLoop 指针。
  - `writeBuffer_`：写缓冲区。
- 核心方法：
  - `handleEvent(revents)`：由 EventLoop 调用，根据事件类型分派到 `handleRead()` 或 `handleWrite()`。
  - `handleRead()`：循环读取数据，提交给 Worker 线程池处理。
  - `send(msg)`：线程安全的发送接口，如果不在 EventLoop 线程则通过 `addTask` 投递。
  - `sendInLoop(msg)`：在 EventLoop 线程内执行的实际发送逻辑，处理 EAGAIN 和开启 EPOLLOUT。

### 6.3 WorkerPool 类
- 线程池，负责执行业务耗时操作。
- 维护一个任务队列和多个工作线程。
- `submit(f)`：将任务放入队列并通知工作线程。
- 工作线程取出任务执行，执行完毕后通过 `conn->send(response)` 将结果交还给 IO 线程。

### 6.4 MainReactor 类
- 只负责接受新连接。
- 拥有自己的 epoll 实例，监听 listen socket 的 `EPOLLIN`。
- `acceptNewConnection()`：循环 `accept4` 直至 EAGAIN，然后轮询选择 SubReactor，通过其 `addTask` 创建 `TcpConnection`。

## 7. 常见问题与陷阱

| 问题 | 原因 | 解决方案 |
|------|------|----------|
| 忙等 / CPU 100% | 水平触发下未读空数据，或 EPOLLOUT 未及时关闭 | 使用边缘触发，写完后立即删除 EPOLLOUT |
| 数据丢失 | 边缘触发下只读了一次，未循环读至 EAGAIN | 读/写/accept 都使用 while 循环直到 EAGAIN |
| 连接饿死 | 某个连接疯狂发数据，IO 线程一直为其服务 | 限制单次处理循环次数（如读16次后主动返回，让 epoll 再次触发） |
| 注册失败或崩溃 | 跨线程直接操作 epoll | 始终通过 `addTask` + `wakeup` 间接操作 |
| 响应乱序/数据竞争 | Worker 线程直接 write 连接 socket | 写操作必须通过 `send()` 交还给所属 IO 线程 |

---

## 8. 总结与适用场景
- **主从 Reactor 模型**通过分层（accept 与 IO 分离）、分片（多个 SubReactor）和异步化（Worker 线程池），实现了高性能、高并发的网络服务。
- **适用场景**：需要支撑海量连接（10k+）且连接上有复杂业务逻辑的服务，如即时通讯、API 网关、游戏服务器等。
- **实现要点回顾**：
  - `MainReactor` 仅 accept，使用轮询分发给 `SubReactor`。
  - `SubReactor` 独立线程 + epoll，通过 `eventfd` + 任务队列处理跨线程注册与写回。
  - `Worker` 线程只做计算，通过 `send` 安全写回，保证无锁。
  - 必须正确处理边缘触发、写缓冲区和 `EPOLLOUT` 的开启与关闭。
