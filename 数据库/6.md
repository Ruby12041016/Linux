# MySQL 学习笔记六

# 一、为什么需要日志

数据库不仅要存储数据。

还要保证：

```text
事务正确
断电不丢数据
支持回滚
支持恢复
支持主从同步
```

---

例如：

```sql
UPDATE account
SET balance = 2000
WHERE id = 1;
```

执行过程中突然：

```text
服务器断电
数据库崩溃
系统宕机
```

数据库必须能够：

```text
恢复数据
保证一致性
```

---

因此MySQL设计了日志系统。

---

# 二、MySQL三大日志

```text
MySQL
│
├── Undo Log
│
├── Redo Log
│
└── Binlog
```

---

作用对比：

| 日志       | 作用   |
| -------- | ---- |
| Undo Log | 回滚事务 |
| Redo Log | 崩溃恢复 |
| Binlog   | 数据同步 |

---

# 三、Undo Log（回滚日志）

## 什么是Undo Log

Undo：

```text
撤销
```

---

Undo Log：

> 保存数据修改前的旧版本数据。

---

例如：

原数据：

```text
balance = 1000
```

执行：

```sql
UPDATE account
SET balance = 2000
WHERE id = 1;
```

---

修改前：

```text
1000
```

会记录到：

```text
Undo Log
```

---

# 四、Undo Log解决什么问题

## 问题1：事务回滚

事务：

```sql
BEGIN;

UPDATE account
SET balance = 2000
WHERE id = 1;

ROLLBACK;
```

---

执行ROLLBACK后：

```text
2000
↓
1000
```

恢复成功。

---

原因：

```text
Undo Log保存了旧数据
```

---

## 问题2：MVCC

MVCC需要：

```text
历史版本数据
```

---

这些历史版本来自：

```text
Undo Log
```

---

# 五、Undo Log工作流程

执行：

```sql
UPDATE account
SET balance = 2000
WHERE id = 1;
```

---

步骤：

```text
1 保存旧值1000

2 写Undo Log

3 修改数据

4 COMMIT或ROLLBACK
```

---

# 六、Undo Log对应ACID

对应：

```text
Atomicity
原子性
```

---

原因：

```text
事务失败时可以撤销
```

---

# 七、Redo Log（重做日志）

## 什么是Redo Log

Redo：

```text
重做
```

---

Redo Log：

> 记录已经完成的数据修改。

---

# 八、为什么需要Redo Log

假设：

```sql
UPDATE account
SET balance = 2000
WHERE id = 1;
```

---

修改后：

```text
内存 = 2000
```

---

磁盘：

```text
1000
```

---

突然断电。

---

内存消失：

```text
2000
```

丢失。

---

怎么办？

---

解决方案：

```text
先记录Redo Log
```

---

即使断电。

也能恢复。

---

# 九、Buffer Pool

InnoDB核心缓存。

---

作用：

```text
缓存数据页
```

---

数据操作实际发生在：

```text
Buffer Pool
```

而不是磁盘。

---

例如：

```sql
UPDATE ...
```

实际：

```text
修改内存
```

---

# 十、脏页（Dirty Page）

磁盘：

```text
1000
```

---

内存：

```text
2000
```

---

状态：

```text
Dirty Page
```

---

定义：

```text
内存与磁盘不一致
```

---

# 十一、WAL机制

WAL：

```text
Write Ahead Logging
```

---

中文：

```text
预写日志
```

---

原则：

```text
先写日志

后写数据
```

---

流程：

```text
修改数据
    ↓
写Redo Log
    ↓
COMMIT
    ↓
后台刷盘
```

---

# 十二、事务提交流程

执行：

```sql
BEGIN;

UPDATE ...

COMMIT;
```

---

内部：

```text
1 修改Buffer Pool

2 生成Redo Log

3 Redo Log落盘

4 COMMIT成功

5 后台刷脏页
```

---

重要结论：

```text
COMMIT成功

≠ 数据页落盘
```

---

而是：

```text
Redo Log落盘
```

---

# 十三、Crash Recovery

Crash：

```text
崩溃
```

---

Recovery：

```text
恢复
```

---

场景：

```text
COMMIT成功
```

---

但：

```text
数据页未落盘
```

---

突然断电。

---

重启后：

```text
读取Redo Log
```

---

重新执行修改。

---

恢复成功。

---

# 十四、Redo Log对应ACID

对应：

```text
Durability
持久性
```

---

保证：

```text
事务提交后不丢失
```

---

# 十五、Redo Log特点

## 优点

顺序写。

速度快。

---

## 缺点

需要额外存储空间。

需要恢复过程。

---

# 十六、Binlog（二进制日志）

## 什么是Binlog

Binlog：

```text
Binary Log
```

---

中文：

```text
二进制日志
```

---

作用：

> 记录所有数据变更操作。

---

# 十七、Binlog记录什么

例如：

```sql
INSERT INTO user
VALUES(1,'Tom');
```

---

Binlog记录：

```text
发生过一次INSERT
```

---

执行：

```sql
UPDATE user
SET age = 20
WHERE id = 1;
```

---

Binlog记录：

```text
发生过一次UPDATE
```

---

# 十八、Binlog作用

## 主从复制

主库：

```text
Master
```

---

从库：

```text
Slave
```

---

结构：

```text
Master
   ↓
 Binlog
   ↓
 Slave
```

---

从库读取Binlog。

执行相同操作。

---

最终：

```text
数据一致
```

---

## 数据恢复

场景：

```text
下午误删数据
```

---

恢复凌晨备份。

---

然后：

```text
重放Binlog
```

恢复到误删前。

---

## 审计

记录：

```text
谁改了数据

什么时候改

改了什么
```

---

# 十九、Binlog三种格式

## Statement

记录SQL。

例如：

```sql
UPDATE user
SET age=20
WHERE id=1;
```

---

优点：

```text
日志小
```

---

缺点：

```text
主从可能不一致
```

---

## Row

记录行变化。

例如：

```text
18 → 20
```

---

优点：

```text
最准确
```

---

缺点：

```text
日志大
```

---

企业默认：

```text
Row
```

---

## Mixed

自动选择：

```text
Statement

或

Row
```

---

# 二十、Redo Log与Binlog区别

| 对比项  | Redo Log | Binlog       |
| ---- | -------- | ------------ |
| 所属层  | InnoDB   | MySQL Server |
| 类型   | 物理日志     | 逻辑日志         |
| 作用   | 崩溃恢复     | 数据同步         |
| 记录内容 | 数据页修改    | SQL变更        |
| 覆盖方式 | 循环覆盖     | 追加写          |
| 主从复制 | 否        | 是            |

---

记忆：

```text
Redo Log
负责自己恢复

Binlog
负责告诉别人发生了什么
```

---

# 二十一、为什么不能互相替代

## Redo Log不能替代Binlog

因为：

```text
只记录数据页修改
```

---

无法知道：

```text
执行了什么SQL
```

---

不适合：

```text
主从复制
```

---

## Binlog不能替代Redo Log

因为：

```text
只记录逻辑操作
```

---

不能保证：

```text
崩溃恢复
```

---

# 二十二、两阶段提交（Two Phase Commit）

## 为什么需要

事务提交时：

```text
Redo Log

Binlog
```

都要写。

---

如果：

```text
Redo成功

Binlog失败
```

会产生不一致。

---

# 二十三、两阶段提交流程

```text
事务提交
     ↓
Redo Log Prepare
     ↓
写Binlog
     ↓
Redo Log Commit
     ↓
事务完成
```

---

流程图：

```text
BEGIN
   ↓
UPDATE
   ↓
Redo Prepare
   ↓
Binlog
   ↓
Redo Commit
   ↓
COMMIT SUCCESS
```

---

作用：

```text
保证Redo Log

与

Binlog一致
```

---

